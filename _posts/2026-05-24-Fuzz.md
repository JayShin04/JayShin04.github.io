# 개요
보안을 공부하다보면 'Fuzzing', 'Fuzzer' 같은 단어를 접하게 된다. <br>
처음에는 퍼징이 단순히 프로그램에 아무 입력값이나 넣어보면서 결과를 확인하는 단순한 작업인 줄 알았으나 
이 글은 퍼저와 퍼징이 무엇인지에 대해 살펴보기 위해 작성되었다.

# 1. Fuzzing과 Fuzzer는 무엇을 뜻하는가?
- **퍼징(Fuzzing)**은 **퍼즈 테스팅(Fuzz Testing)**이라고 불리기도하며, 프로그램에 이상하거나 랜덤한 입력값을 대량으로 넣어보면서 비정상 동작과 취약점을 찾아내는 동적 테스트 기법이다. <br>
- **퍼저(Fuzzer)**는 동적 테스트 기법인 퍼징을 수행할 때 사람이 일일이 입력하며 테스트하기 힘든 퍼징 과정을 컴퓨터가 수행하도록 설계된 도구를 의미한다. <br>

### Fuzz의 시작
시작은 1988년, Barton Miller라는 교수가 Unix 유틸리티에 대한 무작위 입력과 명령줄 인자를 자동으로 생성하여 주입하였떠니 프로그램의 25~33%가 크래시를 일으켰다고 한다. <br>
각 크래시들을 디버깅하고 원인을 파악 및 오류를 분석하며 다른 연구자들이 다른 소프트웨어로 유사한 실험을 수행할 수 있도록 도구의 소스 코드, 테스트 절차, 결과 데이터를 발표했다. <br>
지금은 많은 취약점 연구원들이 새로운 취약점, 버그들을 찾아낼 때 활용하는 기법 중 하나로 자리잡았다.<br>

### Fuzzing의 간단한 예시
만약 개발자가 기대하는 정상적인 입력이 다음과 같다고 가정해보자. <br>

```
username=admin
age=20
file=image.png
```

fuzzing에서는 다음과 같은 값을 넣는다고 할 수 있다. <br>

```
username=AAAAAAAAAAAAAAAAAAAAAAAAAAAAAAA
age=-999999999999999999999999999
file=../../../../../
file=%00%00%00
file=crash.png(내부 구조가 깨진 PNG파일)
```

사람이 직접 어느정도 테스트는 할 수 있껬지만 퍼저를 사용하는 이유는, 퍼징은 퍼저가 엄청 큰 개수의 입력을 자동 생성 및 변형해서 프로그램을 계속 두드려보는 방식이라고 생각하면 된다. <br>

# 2. 퍼징 동작 원리
대부분의 오늘날의 퍼저의 동작 원리는 다음과 같다. <br>
1. 테스트할 프로그램 또는 함수 선택
2. 초기 입력(seed corpus) 준비
3. 입력을 새로 생성(generation)하거나 변형(mutation)
4. 입력값을 프로그램에 넣어 실행
5. 크래시, hang, 새로운 코드 경로 발견 여부 확인
6. 쓸모 있는 입력(새 코드 경로를 만들거나 크래시와 같은 오류를 일으킨 입력)을 저장
7. 반복
<br>

<p>
이 과정이 1초에 수천 회씩 프로그램이 자동으로 반복하며 사람이 직접 발견하기 어려운 버그를 찾아낼 수 있다.
</p>

# 3. Fuzzer의 분류

### 입력값 생성 방식
- Mutation-based Fuzzer: <br>
    Mutation 기반 퍼저는 퍼징 중에 기존의 시드 입력(Seed Corpus)을 활용하며 제공된 시드를 수정 또는 변형하여 입력을 생성한다. <br>

- Generation-based Fuzzer: <br>
    Generation 기반 퍼저는 입력을 처음부터 생성한다. 시드 입력(Seed Corpus)의 존재나 품질에 의존하지 않는다.
### 프로그램의 구조 아는가에 따른 분류
- Black Box Fuzzer: <br>
    프로그램의 내부 구조를 알지 못할 때 무작위로 입력을 생성하는 무작위 테스트 도구이다. <br>
    초당 수백 개의 입력을 실행할 수 있고, 쉽게 병렬화 할 수 있으며, 임의의 크기의 프로그램으로 확장할 수 있다. <br>
    하지만 표면적인 버그만 드러낼 수 있다는 한계점이 존재한다.
- White Box Fuzzer: <br>
    프로그램의 내부 구조를 알 때 사용하는 도구이다. <br>
    프로그램 분석을 활용하여 특정 중요 프로그램 위치에 도달할 수 있다. <br>
    하지만 프로그램 분석에 소요되는 시간이 너무 길어질 수 있으며 이 경우엔 블랙박스 퍼저가 더 효율적일 수 있다.
- Grey Box Fuzzer: <br>
    프로그램 분석 대신 분석을 수행할 수 있도록 소프트웨어를 수정하며 정보를 수집한다. <br>
    분석 중에 코드 커버리지 증가에 대한 정보만 받아오므로 매우 효율적인 취약점 탐지 도구이다. <br>

### 입력 구조 인식 여부에 따른 분류
- Smart(Model-based) Fuzzer: <br>
    입력 모델(문법, 프로토콜, AST 등)을 활용하여 유효한 입력을 생성한다.<br>
    유효 입력 비율이 높아 파서를 통과해 핵심 로직까지 도달할 가능성이 크다.<br>
    단, 입력 모델이 명시적으로 제공되어야 하므로 모델이 독점적이거나 복잡한 경우 적용이 어렵다. <br>
- Dumb(Model-less) Fuzzer: <br>
    입력 모델 없이 시드 파일을 무작위로 변형(비트 뒤집기, 바이트 대체 등)하여 입력을 생성한다. <br>
    다양한 프로그램에 범용적으로 적용 가능하지만, 유효 입력 비율이 낮아 파서 앞단에서 걸러지는 경우가 많다. <br>
    CRC 체크섬처럼 무결성 검증이 있는 경우 유효한 입력 생성에 실패하기 쉽다. <br>

# 4. 퍼징이 필요한 이유
퍼즈 테스트는 프로젝트 요구사항과 무관한 프로그래밍 오류를 찾아낸다. <br>
- 신뢰할 수 없는 출처로부터 입력을 받는 소프트웨어 (보안)
- 두 개의 복잡한 알고리즘의 동등성 검증(정확성 검증)
- 복잡한 입력을 받는 대용량 API의 안정성을 검증하는 것

세 가지에서 퍼즈 테스트가 유용하다. <br>

### 퍼징이 탐지할 수 있는 버그 유형
- **메모리 오류** (C/C++ 한정): <br>
    - Use-after-free
    - 버퍼 오버플로우
    - 초기화되지 않은 메모리 사용
    - 메모리 누수
- **산술 오류**: <br>
    - 0으로 나누기
    - 정수/부동 소수점 오버플로우
    - 잘못된 비트 시프트
- **크래시**: <br>
    - NULL 역참조
    - 처리되지 않은 예외 사항
- **동시성 버그**: <br>
    - 데이터 레이스
    - 데드락
- **리소스 버그**: <br>
    - 메모리 부족
    - 멈춤 혹은 무한 루프
    - 스택 오버플로우 (무한 재귀)
- **논리 버그**: <br>
    - 동일 프로토콜의 두 구현 간 불일치
    - 라운드트립 일관성 오류(예: 입력값을 압축한 후 다시 압축 해제하여 원본과 비교하는 경우)
    - Assertion 실패

# 5. 퍼징의 적용 대상과 실제 성과

### 주요 적용 대상
퍼징은 특히 다음과 같은 프로그램에서 효과적이다.
- 외부 입력을 처리하는 모든 종류의 파서 (XML, PDF 등)
- 미디어 코덱, 압축 라이브러리, 암호화 라이브러리
- 네트워크 프로토콜 및 RPC 라이브러리
- 컴파일러 및 인터프리터, 데이터베이스, 브라우저

### 퍼징 대상 선정 기준
퍼징은 신뢰할 수 없는 입력에 노출된 코드를 우선 대상으로 삼는다.
- 외부 입력을 처리하는 진입점(entry point)을 식별하는 것이 핵심이다.
- 네트워크에 노출된 코드는 기본적으로 비신뢰 입력을 처리한다고 가정할 수 있다.
- 동일 스펙의 두 구현을 비교하여 출력 차이로 버그를 찾는 방식도 유효하다. (암호화 라이브러리, JS 엔진 등)

### 퍼징 성공 사례
AFL, libFuzzer, syzkaller 등의 퍼저를 통해 구글 내외부에서 수만 건의 버그가 발견되었다. <br>
구글은 OSS-Fuzz 서비스를 통해 오픈 소스 프로젝트에 24/7 지속적 퍼징 인프라를 무료로 제공하고 있다. <br>

# 6. 퍼징 도구

퍼저마다 장단점이 있으며, 상황에 따라 적합한 도구가 다르다.

### libFuzzer
유닛 테스트와 유사한 스타일로 퍼즈 타겟을 작성할 수 있는 도구이다. 처음 퍼징을 시작하는 개발자에게 단순함 때문에 권장된다.

### Honggfuzz
다양한 기능을 제공하며 보안 연구원이나 libFuzzer의 단위 테스트 스타일과 유사한 방식으로 작업하기 어려운 복잡한 프로젝트 개발자에게 권장된다.<br>
입력을 커맨드라인, stdin, 또는 네트워크 서버에 직접 주입하는 방식 등을 지원한다.
### AFL / AFL++
커버리지 기반 퍼징의 초기 성공을 이끈 도구이다. 유지보수가 활발히 이루어지지 않기 때문에 새로운 프로젝트에서는 AFL 사용을 권장하지 않는다. <br>
AFL을 기반으로 한 AFL++은 더 나은 유지보수성을 제공하면서 기존 AFL 퍼저와의 호환성도 유지한다. <br>
Docker 이미지로 간편하게 사용할 수 있으며, x86_64와 arm64 모두 지원한다.
#### 커버리지란?
"퍼저가 생성한 입력이 프로그램의 어느 경로까지 실행시켰는가"를 나타내는 지표다. 커버리지 기반 퍼저는 이렇게 새로운 경로를 찾는 입력을 가치있다고 판단하고, 시드 코퍼스에 저장한 뒤 그것을 기반하여 변형을 시도한다. <br>
특정 코드 경로에 버그가 숨어있는 경우가 많은데, 커버리지 피드백 루프로 버그를 발견할 확률이 높아진다.

### Jackalope
블랙박스 바이너리를 대상으로 동작하는 커버리지 기반 퍼지이다. <br>
소스코드가 없는 Windows, macOS, Linux, Android 바이너리 퍼징에 특화되어 있다. <br>
TinyInst 기반 바이너리 계측, 파일/공유 메모리 기반 샘플 전달, 문법 기반 뮤테이션 엔진을 기본 제공한다. <br>
단일 머신에서 멀티스레드로, 또는 서버-클라이언트 구조로 여러 머신에 걸쳐 병렬 퍼징이 가능하다.

## 6-1. AFL / AFL++
### 설치 (Docker 권장)
```bash
docker pull aflplusplus/aflplusplus
docker run -ti -v /path/to/target:/src aflplusplus/aflplusplus
```

### 기본 사용법
먼저 타겟 프로그램을 afl-cc로 컴파일한다.

```bash
CC=/path/to/afl-cc CXX=/path/to/aflc++ ./configure --disable-shared
make clean all
```
<br>
stdin으로 입력을 받는 프로그램을 퍼징할 경우:

```bash
./afl-fuzz -i seeds_dir -o output_dir -- /path/to/tested/program [...program's cmdline...]
```
파일로 입력받는 프로그램의 경우 `@@`를 사용한다. <br>
AFL++가 자동으로 생성한 파일 경로로 치환해준다.

```bash
./afl-fuzz -i seeds_dir -o output_dir -- /path/to/tested/program @@
```

크래시와 hang 결과는 output_dir 하위의 `crashes/`, `hangs/` 디렉토리에 저장된다.
```bash
cat output_dir/crashes/id:000000,* | /path/to/tested/program [...program's cmdline...]
```

## 6-2. Jackalope
### Jackalope 설치

```bash
cd Jackalope
git clone --recurse-submodules git@github.com:googleprojectzero/TinyInst.git
(alternately: git clone --recurse-submodules https://github.com/googleprojectzero/TinyInst.git)
mkdir build
cd build
cmake <generator arguments> ..
cmake --build . --config Release
```

### 기본 사용법
```bash
./fuzzer -in <입력 디렉토리> -out <출력 디렉토리> -t <타임아웃(ms) -instrument_module <모듈명> -- <타겟 실행 명령>
```

| 옵션 | 설명 |
|:----|:------------------|
| -nthreads | 퍼저 스레드 수 (기본값 1) | 
| -delievery <file\|shmem> | 사용할 샘플 전달 메커니즘 |
| -file_extendsion | 샘플 전송 시 file, 지정된 확장자를 파일 이름에 추가 |
| -restore, -resume | 이전 퍼징 세션을 복원하고 재개, 퍼저 프로세스와 서버 프로세스 모두 복원을 지원 |
| -server | 사용할 커버리지 서버를 지정 |
| -start_server | 퍼징 프로세스 대신 서버 프로세스를 실행 |
| -minimize_samples | 코퍼스에 저장하기 전에 새로운 샘플 수를 최소화하려고 시도, 기본값은 true |
| -cmp_coverage | 멀티바이트 비교 브루트포스를 위한 비교 커버리지 사용
| -dict <path> | 뮤테이션에 사용할 딕셔너리 파일 경로 |

#### Jackalope Architecture

##### `Fuzzer` 클래스: <br>
대부분의 상위 수준 작업을 처리하는 메인 클래스다.<br>
문헌에는 Keeping track of corpus and coverage, Scheduling jobs to threads, communicating with the server이라고 나와있다. <br>
직역을 한다면 코퍼스와 커버리지를 추적하고, 작업을 스레드에 배정하고, 서버와 통신을 하는 클래스라는 것인데, 조금 더 알아보자. <br>

1. Keeping track of corpus <br>
    Keeping track of corpus는 퍼저가 보유하고 있는 입력 샘플 집합(Corpus)을 관리하고 기록한다는 뜻이다. <br>
    현재 corpus에 어떤 sample들이 있는지, 어떤 sample이 새 coverage를 만들었는지, 어떤 sample을 다음 변형 대상으로 고를 것인지 등등 샘플을 관리하는 것을 의미한다. <br>
2. Keeping track of coverage <br>
    Coverage는 앞서 설명한 적이 있듯이 "퍼저가 생성한 입력이 프로그램의 어느 경로까지 실행시켰는가"를 나타내는 지표다. 각각의 입력 샘플(corpus)이 프로그램의 어느 코드까지 실행시켰는지 확인하는 것이다. <br>
    따라서 Keeping track of corpus는 프로그램 내부에서 입력 샘플이 어떤 코드 경로를 실행했는지 관리하고 기록하는 뜻이다. <br>
    지금까지 어떤 코드 블록들이 실행되었는지, 이번 입력이 새로운 coverage를 만들었는지, 이 입력을 corpus에 저장할 가치가 있는지 등을 기록한다. <br>
3. Scheduling jobs to threads <br>
    퍼징 작업들을 여러 스레드에 나누어 배정한다는 뜻이다. <br>
    스레드를 간단히 설명하자면 프로그램 안에서 실행되는 작업의 단위라고 보면 된다. 하나의 프로세스에서 여러개의 작업을 한번에 하나씩 처리하지않고 여러 스레드에 나누어주어 동시에 처리할 수 있는 것이다. 스레드는 메모리를 공유하는 특징이 있다. <br>
    어떤 스레드에 어떤 sample을 줄 것인지, 스레드가 놀고 있지는 않는지, 한 sample만 중복해서 너무 많이 돌리고 있지는 않는지, 작업 결과를 어떻게 모을 것인지에 대해 확인하고 관리하는 것을 의미한다. <br>
4. Communicating with the server <br>
    Jackalope는 여러 Fuzzer 프로세스나 여러 머신에서 동시에 돌릴 수 있으며 각 Fuzzer들이 따로 퍼징을 하다가 좋은 입력을 찾는 경우, 서버가 있다면 정보를 공유 할 수 있다는 것을 의미한다. <br>
    새로운 coverage 정보를 서버에 보낸다, 새로운 sample을 서버에 보낸다, 다른 fuzzer가 찾은 sample을 서버로부터 받는다, crash 정보를 공유한다의 의미가 담겨있다. <br>

##### `Sample` 클래스: <br>
입력 데이터를 저장하기 위한 단순한 클래스이다. byte형태로 저장된다. <br>

##### `Mutator` 클래스: <br>
Mutation, 입력 변형을 처리하는 클래스다. <br>
`Mutate()`-샘플을 수정하는 메서드를 구현하는 것이 주요 역할이다. <br>
`Mutate()` 메서드 호출 시 각 샘플에 대한 추가 컨텍스트를 정의하고 호출중에 전달할 수도 있다.
`mutator.h`에서 입력 샘플을 선택 후 '라운드' 동안 퍼징을 수행할 때, '라운드'를 조절할 수 있다. <br>
퍼저는 최상위의 뮤테이터의 메서드가 False로 반환될 때까지 동일한 입력 샘플을 계속 처리한다.

##### `Instrumentation` 클래스: <br>
타겟 실행 및 커버리지를 수집하는 역할을 한다. TinyInst를 사용하는 계측 구현을 포함하고 있다. <br>
잠깐 계측에 대해 간단히 설명하자면, 계측(instrumentation)은 프로그램을 실행할 때 내부에서 무슨 일이 일어났는지 알 수 있도록 추가적인 관찰 장치나 기록 코드를 삽입하는 것을 의미한다. <br>
어떤 basic block이 실행되었는지, 어떤 분기문을 통과했는지, 어떤 edge(코드 블록)간 이동이 발생했는지, 새로운 coverage가 생겨났는지, 프로그램이 timeout이나 crash가 생겼는지 등등 실행 흐름을 볼 수 있게 해주는 것이라고 보면된다. <br>
`Instrumentation`은 jackalope가 coverage-guided fuzzing을 할 수 있게 해주는 핵심 부분이다. <br>
- `TinyInst`가 무엇인가? <br>
TinyInst는 필요한 특정 모듈만 계측하고 나머지 프로세스는 원래대로 실행되게 할 수 있는 가벼운 동적 계측 라이브러리다. <br>


##### `SampleDelivery` 클래스: <br>
샘플을 대상에 저장하는 기능을 담당한다. 퍼저는 파일 및 공유 메모리를 통한 샘플 전달 기능을 기본적으로 제공한다. <br>

##### `PRNG` 클래스: <br>
Mersenne Twister기반의 의사난수 생성기를 사용하여 난수를 생성한다. <br> 입력을 무작위로 바꾸는 과정속 사용하기 위함이다. <br>

##### `Server` 클래스: <br>
fuzzer의 서버 구성 요소를 구현한다. 클라이언트로부터 코드 커버리지를 수집하고, 새로운 커버리지를 트리거하는 샘플을 수집하는 역할을 하며 수집된 샘플을 다른 퍼저 프로세스에 배포한다. Fuzzer 클래스의 Communicating with the server 부분과 상호작용하는 클래스다. <br>

##### `Client` 클래스: <br>
서버와의 통신을 위한 메서드를 구현한다. <br>

Jackalope흐름은 `Fuzzer -> Sample 선택 -> Mutator가 Sample 변형 -> SampleDelivery가 target에 입력 전달 -> Instrumentation이 target에서 입력 실행 및 coverage 수집하며 계측 -> Fuzzer가 corpus/crash/coverage 관리 -> Server/Client가 있으면 다른 Fuzzer와 정보 공유` 로 볼 수 있다. <br>



## 6-3. libFuzzer
프로세스 내부에서 동작하는 커버리지 기반 진화형 퍼징 엔진이다. <br>
테스트 대상 라이브러리와 링크되어 동작하며 LLVM의 SanitizerCoverage 계측을 통해 코드 커버리지 정보를 수집한다.

### 퍼즈 타겟 작성
퍼즈 타겟(Fuzz Target)은 바이트 배열을 입력받아 테스트 대상 API를 호출하는 함수다.

```cpp
// fuzz target.cc
extern "C" int LLVMFuzzerTestOneInput(const uint8_t *Data, size_t Size) {
    DoSomethingInterestingWithMyAPI(Data, Size);
    return 0;
}
```
타겟 함수 작성 시 주의할점: 
- 어떤 입력이 들어와도 exit()을 호출하면 안 된다.
- 가능한 한 결정론적으로 동작해야 한다. 랜덤 동작이 있으면 퍼징 효율이 크게 떨어진다.
- 빠를수록 좋다. 로깅이나 불필요한 메모리 사용을 피한다.
- 반환값 -1을 반환하면 해당 입력을 코퍼스에 추가하지 않는다. (원하지 않는 입력 필터링에 활용)

### 빌드

Clang 6.0 이상에 libFuzzer가 내장되어 있어 별도 설치가 필요 없다.
```bash
# Sanitizer 없이 빌드
clang -g -01 -fsanitize=fuzzer mytarget.c

# AddressSanitizer와 함께 빌드 (권장)
clang -g -01 -fsanitize=fuzzer,adress mytarget.c

# UndefinedBehaviorSanitizer와 함께 빌드
clang -g -01 -fsanitize=fuzzer,signed-integer-overflow mytarget.c
```

### 실행 방법

```bash
# 코퍼스 디렉토리 생성 후 시드 파일 준비
mkdir CORPUS_DIR
cp /some/input/samples/* CORPUS_DIR

# 퍼저 실행
./my_fuzzer CORPUS_DIR
```
새로운 코드 경로를 트리거하는 입력이 발견되면 자동으로 CORPUS_DIR에 저장된다. 크래시 발생 시 `crash-<sha1>`형태의 파일로 저장되며 퍼징이 중단된다.

### 병렬 퍼징
```bash
# 30개의 퍼징 작업을 병렬로 실행 (12코어 기준 워커 6개 자동 할당)
./my_fuzzer -jobs=30 CORPUS_DIR

# 워커 수 직접 지정
./my_fuzzer -jobs=30 -workers=8 CORPUS_DIR
```

### 코퍼스 최소화
코퍼스가 너무 커진 경우 커버리지를 유지하면서 최소화 할 수 있다.
```bash
mkdir NEW_CORPUS_DIR
./my_fuzzer -merge=1 NEW_CORPUS_DIR FULL_CORPUS_DIR
```

| 옵션 | 설명 |
|:----|:------------------|
| -seed=N | 랜덤 시드 지정 |
| -runs=N | 실행 횟수 제한 (-1이면 무한) |
| -max_len=N | 입력 최대 길이 |
| -timeout=N | 타임아웃(초, 기본값 1200) |
| -max_total_time=N | 총 실행시간 제한 (초) |
| -dict=FILE | 딕셔너리 파일 지정 |
| -jobs=N | 병렬 퍼징 작업 수 |
| -workers=N | 병렬 워커 프로세스 수 |
| -merge=1 | 코퍼스 최소화 |
| -minimize_crash=1 | 크래시 입력 최소화 |

### 출력 읽는 법

예시 출력:<br>
`#1345   NEW    cov: 5 ft: 5 corp: 4/8b lim: 14 exec/s: 0 rss: 32Mb`
- `NEW`: 새로운 코드 경로를 트리거하는 입력 발견
- `cov`: 현재까지 커버된 코드 블록 수 
- `corp`: 코퍼스 항목 수 / 전체 크기
- `exec/s`: 초당 실행 횟수
- `rss`: 현재 메모리 사용량

| 주요 사용 사례 | 라이브러리, 파서, 소스 있는 타겟 | 범용, CLI 프로그램, 네트워크 서비스 | 소스 없는 바이너리, Windows/macOS타겟 |




# 8. Sanitizer

<!-- 퍼징의 최종 목표는 버그를 찾는 것이다. 퍼저는 기본적으로 크래시 발생 여부로 버그를 탐지한다. 하지만, 보안상 주요한 버그 중 상당 수는 Overflow나 미정의 입력이 들어왔다고해서 바로 크래시가 나지는 않는다. <br>

### Sanitizer란?
프로그램 실행 중에 메모리 오류, 미정의 동작, 데이터 레이스 같은 문제를 감지하기 위해서 컴파일 단계에서 검사 코드를 삽입하고, 실행 중 오류가 발생하면 즉시 보고하는 동적 분석 도구이다. <br>
<br>
버그가 난다고 해서 바로 DoS가 일어나는 경우만 있는것이 아니다. 오버플로우가 발생하더라도 프로그램이 계속 실행되면, 기존 Fuzzer들은 Crash가 일어나지 않아서 '정상'으로 볼 수 있다.<br>
이때 필요한 것이 Sanitizer이다. 즉, 버그가 발생했을때 어떤 버그인지 감지하는 역할을 의미한다. <br>
<br>
<a href="https://gcc.gnu.org/onlinedocs/gcc/Instrumentation-Options.html">https://gcc.gnu.org/onlinedocs/gcc/Instrumentation-Options.html</a>에 따르면, gcc에서도 sanitizer을 사용할 수 있어서 옵션을 확인할 수 있는데, sanitizer의 종류들을 보여준다. <br>

```
-fsanitize=address
-fsanitize=kernel-address
-fsanitize=hwaddress
-fsanitize=kernel-hwaddress
-fsanitize=memtag-stack
-fsanitize=pointer-compare
-fsanitize=pointer-subtract
-fsanitize=shadow-call-stack
-fsanitize=thread
-fsanitize=leak
-fsanitize=undefined
-fsanitize=memory
-fsanitize=thread
...
```
대표적인 예시들을 살펴보자. <br>
- **AddressSanitizer**: <br>
    메모리 접근 오류를 잡는 가장 대표적인 Sanitizer다. <br>
    감지 목록: <br>
    - 오버플로우, UAF(use-after-free), double-free 일부 등
    감지 후 보고방식: <br>
    
    ```
==9901==ERROR: AddressSanitizer: heap-use-after-free on address 0x60700000dfb5 at pc 0x45917b bp 0x7fff4490c700 sp 0x7fff4490c6f8
READ of size 1 at 0x60700000dfb5 thread T0
    #0 0x45917a in main use-after-free.c:5
    #1 0x7fce9f25e76c in __libc_start_main /build/buildd/eglibc-2.15/csu/libc-start.c:226
    #2 0x459074 in _start (a.out+0x459074)
0x60700000dfb5 is located 5 bytes inside of 80-byte region [0x60700000dfb0,0x60700000e000)

    #0 0x4441ee in __interceptor_free projects/compiler-rt/lib/asan/asan_malloc_linux.cc:64
    #1 0x45914a in main use-after-free.c:4
    #2 0x7fce9f25e76c in __libc_start_main /build/buildd/eglibc-2.15/csu/libc-start.c:226
previously allocated by thread T0 here:
    #0 0x44436e in __interceptor_malloc projects/compiler-rt/lib/asan/asan_malloc_linux.cc:74
    #1 0x45913f in main use-after-free.c:3
    #2 0x7fce9f25e76c in __libc_start_main /build/buildd/eglibc-2.15/csu/libc-start.c:226
SUMMARY: AddressSanitizer: heap-use-after-free use-after-free.c:5 main
    ```
    `ERROR: AddressSanitizer: heap-use-after-free ...`처럼, 확인할 수 있다. 출처: <a href="https://github.com/google/sanitizers/wiki/AddressSanitizer">https://github.com/google/sanitizers/wiki/AddressSanitizer</a> <br>


- **UndefinedBehaviorSanitizer**: <br>
    다양한 형태의 미정의 동작을 탐지한다.
    - signed integer overflow
    - 0으로 나누기
    - 잘못된 shift 연산
    - null pointer에 대한 잘못된 참조
    - misaligned pointer 사용
    - 잘못된 enum 값

    감지 후 출력 방식: <br>
    
    ```
    test.cc:3:5: runtime error: signed integer overflow: 2147483647 + 1 cannot be represented in type 'int'
    ```

- **MemorySanitizer**: <br>
    초기화되지 않은 메모리 읽기를 감지한다. 매우 유용한 도구이나 모든 종속 항목도 계측(Instrument)해야 하므로 다른 도구보다 사용하기가 훨씬 더 까다로울 수 있다.<br>
    
    감지 후 출력 방식: <br>

    ```
    WARNING: MemorySanitizer: use-of-uninitialized-value
0 0x7f45944b418a in main umr.cc:6
1 0x7f45938b676c in __libc_start_main libc-start.c:226
    ```

<br>
일부 Sanitizer은 같이 쓰기 어렵다. <br>
-fsanitize=address, undefined처럼 AddressSanitizer과 UndefinedBehaviorSanitizer은 같이 많이 쓰나 ThreadSanitizer는 별도로, MemorySanitizer도 별도 환경이 필요한 경우가 많다.<br>
<br>
대표적인 AddressSanitizer의 출력방식은 위와 같은데, 출력에서 봐야 할것은 다음과 같다. <br>

1. 무슨 오류인가?
2. READ인가 WRITE인가?
3. 몇 바이트 접근인가?
4. 어느 주소인가?
5. 어느 함수/파일/라인에서 발생했는가?
6. 해당 메모리는 어디서 할당되었는가?
7. 어디서 free 되었는가?

<br>
Sanitizer은 퍼징이 crash가 나지 않아 미처 놓친 부분을 탐지할 수 있는 보조 도구일 뿐이지, 모든 취약점을 탐지할 수 있는 도구는 아니다. 내부 버그를 명확한 report로 드러내는 도구이다. <br>
