## XSS(Cross Site Scripting)
공격자가 웹 리소스에 악성 스크립트를 삽입하여 이용자의 웹 브라우저에서 해당 스크립트를 실행하게끔 하는 클라이언트 사이드 취약점 중 하나이다.

### 클라이언트 사이드 & 서버 사이드?
클라이언트 사이드와 서버 사이드는 웹 개발 용어로, 애플리케이션 코드가 실행되는 위치를 말한다.<br>
<br>
클라이언트 사이드란 웹 애플리케이션에서 클라이언트에 표시되거나 발생하는 모든 것을 의미한다. <br>
텍스트, 이미지 등등 UI나 사용자에게 표시되는 내용, 애플리케이션이 사용자의 브라우저 내에서 실행되는 모든 것이 포함된다.<br>
<br>
HTML, CSS도 클라이언트 사이드의 브라우저에서 해석되며, 대부분의 클라이언트 사이드 프로세스는 JavaScript로 작성된다.<br>
마우스를 특정한 구역에 갖다대면 나타나는 이벤트 또한 서버를 거치지 않고 클라이언트 브라우저에서 해석되는 클라이언트 사이드 프로세스의 예시이다. <br>
<br>
서버 사이드란 웹 애플리케이션에서 클라이언트가 아닌 서버에서 일어나는 모든 일을 의미한다.<br>
과거에는 대부분의 비즈니스 로직이 서버 사이드에서 실행되었고, 동적 웹 페이지 렌더링, 데이터베이스와의 상호작용, 신원 인증 등등이 포함된다.<br>

## XSS의 예시
XSS(Cross Site Scripting, 교차 사이트 스크립팅) 공격의 대표적인 예시로는 필터링을 거치지 않는 댓글이나 게시글 포럼이 있는 사이트에서 흔히 발생한다.<br>
공격자는 `<script></script>` 태그로 감싼 실행 코드로 구성된 댓글이나 게시글을 작성하고, 이 태그는 웹 브라우저에서 태그 사이의 모든 내용을 JavaScript 코드로 해석하며 다른 사용자가 웹 사이트를 로드할 때 스크립트 태그 사이의 악성 스크립트문이 웹 사이트에서 실행되며 그 사용자가 공격의 피해자가 될 수 있다.<br>

from flask import Flask, request, render_template
from selenium import webdriver
from selenium.webdriver.chrome.service import Service
import urllib
import os

app = Flask(__name__)
app.secret_key = os.urandom(32)

try:
    FLAG = open("./flag.txt", "r").read()
except:
    FLAG = "[**FLAG**]"


def read_url(url, cookie={"name": "name", "value": "value"}):
    cookie.update({"domain": "127.0.0.1"})
    try:
        service = Service(executable_path="/chromedriver")
        options = webdriver.ChromeOptions()
        for _ in [
            "headless",
            "window-size=1920x1080",
            "disable-gpu",
            "no-sandbox",
            "disable-dev-shm-usage",
        ]:
            options.add_argument(_)
        driver = webdriver.Chrome(service=service, options=options)
        driver.implicitly_wait(3)
        driver.set_page_load_timeout(3)
        driver.get("http://127.0.0.1:8000/")
        driver.add_cookie(cookie)
        driver.get(url)
    except Exception as e:
        driver.quit()
        # return str(e)
        return False
    driver.quit()
    return True


def check_xss(param, cookie={"name": "name", "value": "value"}):
    url = f"http://127.0.0.1:8000/vuln?param={urllib.parse.quote(param)}"
    return read_url(url, cookie)


@app.route("/")
def index():
    return render_template("index.html")


@app.route("/vuln")
def vuln():
    param = request.args.get("param", "")
    return param


@app.route("/flag", methods=["GET", "POST"])
def flag():
    if request.method == "GET":
        return render_template("flag.html")
    elif request.method == "POST":
        param = request.form.get("param")
        if not check_xss(param, {"name": "flag", "value": FLAG.strip()}):
            return '<script>alert("wrong??");history.go(-1);</script>'

        return '<script>alert("good");history.go(-1);</script>'


memo_text = ""


@app.route("/memo")
def memo():
    global memo_text
    text = request.args.get("memo", "")
    memo_text += text + "\n"
    return render_template("memo.html", memo=memo_text)


app.run(host="0.0.0.0", port=8000)

read_url함수 부분에서 headless Chrome의 방식으로 admin권한을 가진 봇이 존재하며, 이 xss-1의 엔드포인트는 총 네가지이다. <br>
'/' 페이지, '/vuln'페이지, '/flag'페이지, '/memo'페이지 <br>
특히 /vuln페이지에서는 param의 파라미터를 아무런 검증 없이 받고 리턴해주기 때문에 `<script></script>`같은 경우도 그대로 실행하는 취약점이 발생한다.<br>
/flag페이지에서는 POST 요청으로 param 값을 파라미터로 받고,{"name": "flag", "value": FLAG.strip()}인 실제 FLAG값을 check_xss -> read_url로 어드민 봇을 가진 봇에게 넘겨주게된다. 이때, 어드민 봇은 쿠키를 파라미터로 가진상태에서, '/'페이지에 접속한 뒤 FLAG쿠키를 심고, 공격 URL로 이동하게 된다.<br>
`<script>location.href = "http://127.0.0.1:8000/memo?memo=" + document.cookie</script>`<br>
따라서 위와 같은 스크립트문을 /flag페이지에 넣고 POST요청을 보내게된다면, "http://127.0.0.1:8000/vuln?param=http://127.0.0.1:8000/memo?memo=<쿠키값>"과 같은 요청과 똑같아지며, /memo페이지에서는 memo파라미터로 받은 뒷부분을 전부 평문 형태로 저장하기 때문에, 어드민 봇이 가지고있는 쿠키값(FLAG)이 기록된다. <br>
