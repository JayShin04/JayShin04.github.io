# 기본 명령어
- Commit <br>
    - Commit은 Git 저장소에 디렉토리에 있는 모든 파일에 대한 '스냅샷'을 기록하는 것이다.
    - 각 커밋은 저장소의 이전 버전과 다음 버전의 변경 내역("delta")를 저장한다. 대부분의 커밋이 그 커밋 위의 부모 커밋을 가리키게 된다.
    - 명령어 : `git commit`
    - `--amend`: 커밋 내용 정정
- Branch
    - 브랜치는 특정 커밋에 대한 참조(reference)라고 할 수 있다.
    - 브랜치를 많이 만들어도 메모리나 디스크 공간에 부담이 되지 않기 때문에, 작업을 작은 단위로 잘게 나누는 것이 좋다. 하나의 커밋과 그 부모 커밋들을 포함하는 작업 내역이라고 생각하면 된다.
    - 명령어 : `git branch <브랜치명>`
    - option: `-f`
        - 브랜치를 특정 커밋에 직접적으로 재지정 할 수 있다.
        - 예시: `git branch -f main HEAD~3`
- Checkout
    - 브랜치를 생성하고 새 브랜치로 이동할 때 사용하는 명령어다.
    - 명령어: `git checkout <브랜치명>`
    - HEAD
        - HEAD는 현재 체크아웃된 커밋을 가리킨다.
        - 가장 최근 커밋을 가리키며, C1커밋이 있다면 커밋에 직접 checkout을 하여 HEAD를 분리시킬 수 있다.
- Merge
    - 두 별도의 브랜치를 합치는 방법이다.
    - 두 개의 부모를 가리키는 특별한 커밋을 만들어낸다.
    - 한 부모의 모든 작업 내역과 나머지 부모의 모든 작업, 그리고 각각의 모든 부모의 작업 내역을 포함한다.
    - 명령어 : `git merge <브랜치명>`
    - 메모: merge하게 되면 checkout 된 곳에서 최종 커밋이된다.
- Rebase
    - 브랜치끼리의 작업을 접목하는 방법이다.
    - 기본적으로 커밋들을 모아서 복사한 뒤 아래로 내리는 작업, 커밋들의 흐름을 보기 좋게 한 줄로 만들 수 있다는 장점이 있다. 커밋 로그와 이력이 한결 깨끗해진다.
    - checkout 된 곳에서 브랜치 아래로 이동할 곳에 rebase한다.
    - 이미 내려간 branch에서 fast-forward 기능도 있음
        - 예를 들어, `bugFix`라는 브랜치의 내용을 `main`에 넣으려할때, 간단히 최신 커밋으로 `main`을 이동시킨다면, 디버그용 코드들도 함께 들어가서 지저분해짐. `cherry-pick`이나 `rebase`사용
    - 명령어 : `git rebase <브랜치명>`
    - option: `-i`
        - 인터랙티브 리베이스, 리베이스의 목적지가 되는 곳 아래에 복사될 커밋들을 보여주는 UI를 띄워준다.
        - `git rebase -i HEAD~4`
        - 적용할 커밋들의 순서를 UI를 통해 바꿀 수 있다.
        - 원하지 않는 커밋들을 뺄 수 있다.
        - 커밋을 Squash 할 수 있다. (커밋을 합칠 수 있다.)
- Reset / Revert
    - git에는 작업한 것을 되돌리는 방법이 크게 두가지로 볼 수 있다.
    - Reset: 커밋을 하지 않은 것 처럼 히스토리를 건드림
    - Revert: 커밋 내용과 반대되는 내용을 새로 커밋한것처럼 만듦
    - 명령어: `git reset HEAD~1`
    - 명령어: `git revert HEAD`
    - 메모: revert를 하게 되면 다른 작업자들에게도 변경 내역을 push 해줄수있다.
- cherry-pick
    - 현재 위치(HEAD) 아래에 있는 일련의 커밋들에 대한 복사본을 만들겠다는 것을 간단히 줄인 말
    - 명령어: `git cherry-pick <Commit1> <Commit2> <...>`
    - checkout 된 곳 밑으로 `<Commit1>` 부분들을 복사본을 가져온다.
- Git Tag
    - 브랜치는 쉽게 변하고, 이동하기 쉽다. 중요한 지점들에 영구적인 표시할 때 사용하는 방법
    - Git 태그는 특정 커밋들을 브랜치로 참조하듯이 영구적인 이정표처럼 표시한다. 커밋들이 추가적으로 생성되어도 절대 움직이지 않는다.
    - 명령어: `git tag <tag name> <commit>`
- Git Decribe
    - 가장 가까운 태그에 비해 상대적으로 어디에 위치해있는지 묘사해주는 명령어
    - 명령어: `git describe <ref>`
        - `<ref>`에는 commit을 의미하는 그 어떤 것이던 쓸 수 있다. 특정지어주지 않으면, 체크아웃된 곳을 사용한다.
        - 출력은 `<tag>-<numCommits>-g<hash>`로 나타난다.
        - `<tag>`는 가장 가까운 부모 태그, `<numCommits>`은 그 태그가 몇 커밋 멀리 있는지, `<hash>`는 묘사하고 있는 커밋의 해시를 나타낸다.<br>

# 알아야 할 연산자
- 상대 참조(^, ~)
    - git log로 커밋의 해시들을 직접 타이핑 할 수도 있고, 앞 4글자만 입력해도 사용이 가능하지만, 불편함
    - 그렇기에 상대참조를 쓴다.
    - `^`
        - 한 커밋 위로 움직인다.
        - `<branch or commit>^`
        - 병합이된 커밋에서 어떤 부모를 참조할지 선택하는 기능도 있다.
        - 예시: `git checkout main^2`
            - 병합된 곳에서 다른 부모를 선택하는 방법이다.
    - `~`
        - 한번에 여러 커밋 위로 올라갈 수 있다.
        - `<branch or commit>~<num>`
        - 예시: `git rebase -i HEAD~4`

# 원격에서 쓰이는 명령어
- git 저장소? 원격 저장소?
    - git 저장소는 커밋들로 이전의 상태로 되돌리는 기능을 갖고 있다. 하지만 그 모든 정보가 로컬(내 PC)에 저장되어있다.
    - 만약, 우리의 git 저장소를 다른 컴퓨터가 복사본으로 가지고 있다면, 로컬 데이터를 다 잃더라도 다른 컴퓨터에 남아있는 복사본으로 다시 시작할 수 있다.
    - 그렇기에 우리는 원격 저장소에 저장을 해두고 복사본을 만드는 식으로 작업을 한다. (공동 제작에도 쓰이는 흔한 방법이다.)
- git clone
    - 원격 저장소에 있는 데이터를 복사본을 가져와 로컬에 생성할 때 사용하는 명령어다.
    - 명령어: `git clone`
    - origin main이라고 하는 새 브랜치가 생성이 된다. 원격 브랜치라고 부른다.
        - 원격 브랜치는 원격 저장소의 상태를 반영한다. 로컬에서의 작업과 공개적으로 되고있는 작업의 차이를 이해하는데에 도움을 준다.
        - 원격 브랜치는 체크아웃을 하게되면 분리된 HEAD 모드로 가게 되는 속성이 있다. (브랜치에서 직접 작업할 수 없기 때문 -> 다른곳에서 작업을 하고 원격 저장소에 공유를 하는 방법으로 원격 브랜치를 갱신한다.)
- git fetch
    - git 원격 작업은 서로 다른 저장소에서 데이터를 주고 받는 것이다.
    - git fetch는 원격 저장소에서 데이터를 가져오는 방법이다.
    - 원격 저장소에는 있지만 로컬에는 없는 커밋들을 다운로드하고, 원격 브랜치가 가리키는 곳을 업데이트한다.
    - git fetch는 일반적으로 원격 저장소와 인터넷을 통해 접근한다. (`http://`, `git://` 같은 프로토콜)
    - 주의할점은, 로컬 상태를 바꾸지 않는다.
    - 명령어: `git fetch`
    - 인자들: 
        - `git fetch origin <branch name>`
            - 예를들어 branch name이 `foo`라면, 원격 저장소의 foo브랜치로 가서 현재 로컬에 없는 커밋들을 가져와 로컬의 `o/foo`브랜치 아래에 추가할 것.
        - `git fetch origin <source>:<destination>`
            - `<source>`는 이제 받아올 커밋이 있는 원격에 있는 place를 넣어줘야하고 `<destination>`은 그 커밋들을 받아올 local의 place를 인자로 넣어줘야한다. git push와 정반대
- git pull
    - 원격저장소의 변경을 fetch하고, merge하는 작업의 과정을 한번에 하는 명령어다.
    - 명령어: `git pull`
    - option: `--rebase`
        - 로컬에서 작업하고 있는 push할 commit이 이미 변경된 내용보다 구 버전일때, 히스토리가 엇갈리게 된다.
        - 작업을 원격 브랜치의 최신 상태로 만들어야한다.
        - `git fetch; git rebase origin main; git push`
        - 이 방법으로, fetch와 rebase를 통해 push를 정상적으로 할 수 있으며, 이것을 줄인것이 --rebase 옵션이다.
        - 명령어: `git pull --rebase`
    - 인자들:
        - `git pull <remote> <place>`
        - `git pull origin <source>:<destination>`
- git push
    - 자신의 작업 변경 내역을 원격 저장소에 업로드하고 새 커밋들과 합쳐 갱신하게 한다. 원격 저장소에서 우리의 작업을 내려받을 수 있게된다.
    - 명령어: `git push`
    - 인자들: 
        - `git push <remote> <place>`
        - `git push origin <source>:<destination>`
            - 콜론 참조 스펙, git이 알아낼 수 있는 위치를 이름 붙여서 말하는 것.
            - 예시: `git push origin main:newBranch` : main자리에 origin newBranch 생성 후 push
- pull request
    - 규모가 큰 개발팀에서, 원격저장소의 main으로 바로 push하는것은 잠겨있다.
    - 해결책: 
        - feature로 다른 이름의 브랜치를 만들어 원격 저장소에 push, 원격 저장소와 동기화 될 수 있도록 로컬 저장소의 main 브랜치를 reset (`git branch -f main o/main`)
- 원격 추적 브랜치
    - pull 작업을 하는 도중, 커밋들은 origin main에 내려받아지고 그다음 main브랜치로 merge된다.
    - push 작업을 하는 도중, main 브랜치의 작업은 원격의 main브랜치로 push된다.
    - 아무 임의의 브랜치를 origin main을 추적하게끔 만들 수도 있다.
    - 명령어: `git checkout -b <branch name> <origin main>`
        - 메모: 브랜치가 있으면 불가능하다
    - 명령어2: `git branch -u <origin main> <branch name>`
